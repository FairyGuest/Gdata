## 一、User Prompt

请你给我完成一个 NFT 固定价挂单市场服务系统，支持挂单、取消与成交结算，结算含按比例版税拆分，并对 soulbound 资产拒绝一切交易。

任务环境：从空目录开始，主要技术栈为 TypeScript、Node.js、Fastify、SQLite。

任务约束：所有数据和外部参与者使用本地合成夹具或明确的本地依赖，不需要生产账号和真实业务数据。夹具以固定种子生成初始账本（collections 含版税与 soulbound 配置、代币所有权、用户余额）；并发成交以内部事务提交序号裁决，不依赖真实时钟或网络时序。以最小可验收实现为目标，不实现语义规格之外的抽象、优化或扩展。

语义规格：

- 正例
  - 挂单与取消：同一 token 已有有效挂单时再次挂单返回 409；取消仅限创建者；已成交订单不可取消（409）——均带可区分 reason
  - 成交原子性与并发裁决：accept 时卖方必须仍持有该 token（否则挂单失效 409）；所有权转移、买方扣款、版税与卖方入账在同一 SQLite 事务内提交；并发双 accept 以提交序号裁决，恰有一个成功
  - 版税拆分与快照一致性：royalty = floor(price × bps / 10000)，卖方得 price − royalty，买方实付恒为 price；拆分配置以挂单创建时的 collection 快照为准，此后修改不影响已挂订单；成交响应中的新所有者、成交价与拆分金额来自同一提交快照
  - soulbound：soulbound collection 的挂单与成交一律拒绝，返回与普通冲突可区分的失败类别（policy 类冲突，独立 reason）
- 负例
  - 不把撮合写成"先翻转订单状态再补账"：任一时刻账本守恒（余额变动之和 = 0，拆分之和 = 成交价）
  - 不以请求到达的时间戳裁决并发；以事务提交序号为准
  - 不把 soulbound 校验交给前端或文档约定；服务端必须拒绝并返回可区分错误

工程结构：工程边界至少覆盖契约解析、执行内核、状态适配、诊断接口，模块间的数据与错误契约要明确；提供独立的测试和配置层；不要把全部实现塞进一个文件，也不要为凑文件数拆空壳。

- `src/contract/`：挂单/取消/成交参数解析，价格、bps（0–10000）与资产存在性校验
- `src/kernel/`：成交内核：事务边界、守恒断言、提交序号并发裁决
- `src/state/`：SQLite 账本（所有权、余额、订单簿）、collection 快照存取与迁移
- `src/diag/`：订单状态转移日志、每次成交的拆分明细与判定理由

验证：

- 并发双买家 accept 同一挂单：断言恰有一个 200 与一个 409，所有权仅转移一次，账本守恒
- 版税非整除（price=1003、bps=250）：断言 royalty=25、卖方得 978，与独立算术对照
- soulbound collection 的挂单与成交：断言被拒，失败类别与"重复挂单"类冲突可区分

测试质量：独立测试应断言具体结果及失败类别，不只检查"接口能调用"；参考答案不能全部由被测核心实现自身生成。

可诊断性：测试日志应保留能够重放问题的运行编号、关键中间状态和判断理由，适用的输入错误、状态冲突、资源耗尽与计算失败须可区分；不要把异常或未知状态统一返回成功。

错误分类：422 输入错误（价格非正整数、bps 越界、未知资产）；409 状态冲突（重复挂单、已成交/已取消、卖方不持有、余额不足、soulbound 交易——均带可区分 reason）；503 资源耗尽（锁等待超时）；500 计算失败（守恒断言失败）。每次成交记录：运行编号、订单 id、状态转移、拆分明细与判定依据。

验收：提供依赖清单与一键验收脚本 `npm run accept`，按固定顺序演练上述全部场景，逐步打印请求、响应与判定，全部通过退出 0、任一失败非 0 退出并指出失败场景；README 写清错误语义与复现步骤，测试实际执行并报告结果。
