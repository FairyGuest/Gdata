请你给我完成一个 NFT 抵押借贷服务系统：借入即锁定 NFT 作质押托管，利息按内部 tick 序号累积，支持恰额赎回与跌破估值线的清算，全程账本守恒。

任务环境：从空目录开始，主要技术栈为 TypeScript、Node.js、Fastify、SQLite。

任务约束：所有数据和外部参与者使用本地合成夹具或明确的本地依赖，不需要生产账号和真实业务数据。夹具以固定种子生成初始账本（NFT 估值表按 tick 阶梯变化、用户余额）；tick 为全局单调序号，每笔写请求（借入/还款/清算）使其 +1；并发清算以内部事务提交序号裁决，不依赖真实时钟或网络时序。以最小可验收实现为目标，不实现语义规格之外的抽象、优化或扩展。

语义规格：

- 正例
  - 借入与质押：创建借款即把抵押 token 转入托管（原持有者不再持有），放款与质押在同一 SQLite 事务内提交；借款金额须满足 金额 ≤ 当前估值 × 质押率（bps），否则 409（insufficient_collateral）
  - 利息与逻辑时间：应付债务 = 本金 + floor(本金 × perTickBps × 已过 tick / 10000)，已过 tick 按借入时与结算时的全局 tick 差计算；估值取结算时 tick 对应的阶梯值
  - 还款与赎回：还款金额 ≥ 应付即成交，差额同事务退回，抵押 token 同事务赎回给借入者；已清算/已赎回的借款不可再还款（409）
  - 清算：当前估值 < 应付债务 × 清算线（bps）时任何人可发起清算，抵押转给资金方、债务消除；未达清算线清算 409；并发双清算以提交序号裁决，恰有一个成功
- 负例
  - 不把清算写成"先转移质押再记台账"
  - 不以请求到达的时间戳计息或裁决并发；一律用 tick 与事务提交序号
  - 不把估值写成随机的或外部拉取的；只用夹具阶梯表

工程结构：工程边界至少覆盖契约解析、执行内核、状态适配、诊断接口，模块间的数据与错误契约要明确；提供独立的测试和配置层；不要把全部实现塞进一个文件，也不要为凑文件数拆空壳。

- `src/contract/`：借入/还款/清算参数解析，金额与费率（bps 0–10000）校验
- `src/kernel/`：借贷内核：利息算术、事务边界、提交序号并发裁决
- `src/state/`：SQLite 账本（余额、借款单、托管所有权）、估值阶梯表存取与迁移
- `src/diag/`：借款单状态与结算结果的只读查询

验证：

- 并发双清算同一借款：断言恰有一个 200 与一个 409，抵押仅转移一次，账本守恒
- 利息非整除（本金=1003、perTickBps=5、已过 tick=7）：断言利息 = floor(35.105) = 35、应付 1038，与独立算术对照
- 质押与还款边界：超额借入 409、还款不足 409、多还部分如数退回——reason 可区分且账本守恒

测试质量：独立测试应断言具体结果及失败类别，不只检查"接口能调用"；参考答案不能全部由被测核心实现自身生成。

可诊断性：测试日志应保留能够重放问题的运行编号、关键中间状态和判断理由，适用的输入错误、状态冲突、资源耗尽与计算失败须可区分；不要把异常或未知状态统一返回成功。

错误分类：422 输入错误；409 状态冲突；503 资源耗尽；500 计算失败——各类均带可区分的独立 reason。

验收：提供依赖清单与一键验收脚本 `npm run accept`，按固定顺序演练上述全部场景，逐步打印请求、响应与判定，全部通过退出 0、任一失败非 0 退出并指出失败场景；README 写清错误语义与复现步骤，测试实际执行并报告结果。
