请你给我完成一个动态 NFT 元数据服务系统：token 的特征随 XP 喂给与等级跃迁而演化，元数据由状态与模板纯函数渲染，并发喂给不得丢失更新。

任务环境：从空目录开始，主要技术栈为 TypeScript、Node.js、Fastify、SQLite。

任务约束：所有数据和外部参与者使用本地合成夹具或明确的本地依赖，不需要生产账号和真实业务数据。夹具以固定种子生成 collections（等级模板、XP 阈值阶梯）、初始 token 与管理员表；并发喂给以内部事务提交序号串行化，不依赖真实时钟或网络时序。以最小可验收实现为目标，不实现语义规格之外的抽象、优化或扩展。

语义规格：

- 正例
  - 确定性渲染：metadata(token) = f(当前等级、当前 XP、collection 模板)，同一状态多次渲染逐字节一致；等级相关字段（名称、tier、图像引用）随等级变化，其余字段不变
  - XP 与跃迁：feed 累积 XP，达到阈值即升级并扣减对应阈值（阈值阶梯来自夹具），余量结转；升级与 XP 记账在同一 SQLite 事务内提交
  - 并发喂给：并发 feed 同一 token 串行化后每笔都生效，不得丢失更新；总账守恒（Σ喂给量 = Σ已消耗阈值 + Σ当前 XP 余额）
  - 重置与满级：仅 collection 管理员可 reset（回等级 1、XP 0），重置后渲染立即反映；满级后再 feed 409（max_level_reached）
- 负例
  - 不把渲染时间、随机数或请求 id 掺进 metadata
  - 不用"最后写入覆盖"处理并发 feed；不得丢失任一笔
  - 不把模板渲染交给前端拼装；服务端返回完整 metadata

工程结构：工程边界至少覆盖契约解析、执行内核、状态适配、诊断接口，模块间的数据与错误契约要明确；提供独立的测试和配置层；不要把全部实现塞进一个文件，也不要为凑文件数拆空壳。

- `src/contract/`：feed/reset/metadata 参数解析，XP 数值与权限校验
- `src/kernel/`：演化内核：阈值阶梯、跃迁算术、事务边界
- `src/state/`：SQLite 状态（等级、XP、阈值阶梯、管理员表）与迁移
- `src/diag/`：等级与跃迁历史的只读查询

验证：

- 并发双 feed 同一 token：断言两笔都 200、串行化后无丢失更新，总账守恒，等级跃迁与 XP 结转正确
- 阶梯非整除（阈值=7，先 feed 5 再 feed 4）：断言升 1 级、XP=2，与独立算术对照
- 渲染确定性：同一状态渲染两次逐字节一致；升级前后 metadata 差异恰为等级相关字段

测试质量：独立测试应断言具体结果及失败类别，不只检查"接口能调用"；参考答案不能全部由被测核心实现自身生成。

可诊断性：测试日志应保留能够重放问题的运行编号、关键中间状态和判断理由，适用的输入错误、状态冲突、资源耗尽与计算失败须可区分；不要把异常或未知状态统一返回成功。

错误分类：422 输入错误；409 状态冲突；503 资源耗尽；500 计算失败——各类均带可区分的独立 reason。

验收：提供依赖清单与一键验收脚本 `npm run accept`，按固定顺序演练上述全部场景，逐步打印请求、响应与判定，全部通过退出 0、任一失败非 0 退出并指出失败场景；README 写清错误语义与复现步骤，测试实际执行并报告结果。
